# 구조 설명

## 왜 새로 짰나

v1(`index.html`)은 7,500줄짜리 HTML 파일 하나였다. 돌아가긴 했지만 세 가지가 막혀 있었다.

1. **페이지가 하나뿐** — 공유 링크에 유형별 썸네일을 띄울 수 없고, 검색엔진에 걸릴 페이지도 하나였다
2. **문항 100개** — 돌려본 사람들이 길다고 했다
3. **한 파일** — 둘이 같이 고치면 충돌이 난다

v2는 이 셋을 구조로 푼다. 반대로 v1에서 잘 돌아가던 것(문항 데이터, 채점 정규화)은 그대로 가져왔다.

## 폴더

```

    intro.json         기본 질문 7개

    select.ts          문항 뽑는 규칙        ← 자주 바뀔 곳

```

## 서사와 문항이 분리돼 있다

이게 v2의 핵심이다.

`scenes.ts` 는 **이야기만** 갖는다. 어떤 문항이 나올지는 "이 뱅크에서 하나" 라고만 적는다.

```ts
{ kind: 'question', slot: { from: 'ch3-crush' } }
```

`select.ts` 가 실행 시점에 실제 문항을 채운다. 그래서:

- 문항 내용을 바꿔도 → 이야기는 그대로
- 이야기를 바꿔도 → 채점은 그대로
- 뽑는 규칙을 바꿔도 → 위 둘 다 그대로

특정 문항을 꼭 그 자리에 넣고 싶으면 `slot: { id: 'c3-05' }` 처럼 고정하면 된다.

## 시간과 관계 단계는 다른 축이다

처음에는 "1장면 = 1뱅크" 였다. 뱅크(`ch1`~`ch7`)가 **관계 단계**로 나뉘어 있는데
장면은 **시간대**로 나뉘어 있어서, 하루 안에 연애 전체 아크가 강제로 들어갔다.
결과는 이랬다.

```
17:40 하굣길   Q 사귄 지 한 달. 하루 연락 빈도로 적당한 건?   ← 아직 사귀지도 않았는데
23:10 침대 위  Q 헤어진 뒤에 남은 물건들
```

그래서 축을 둘로 분리했다.

| | 어디에 | 무슨 뜻 |
| --- | --- | --- |
| 자리 | 문항의 `where` | 이 문항이 성립하려면 어디에 있어야 하는가 |
| 단계 | 문항의 `ch` | 이 문항이 전제하는 관계 단계 |

장면은 `accepts`(받을 자리)와 `stages`(다룰 단계)를 선언하고, 둘 다 맞는 문항만 받는다.

**자리는 하드 필터, 단계는 소프트다.** 급식실 문항이 새벽 침대에 뜨는 건 바로 눈에 띄지만,
단계까지 하드로 걸면 특정 자기소개 조합에서 문항이 말라 검사 길이가 사람마다 달라진다.
길이가 달라지면 채점이 흔들린다.

부수 효과가 하나 더 있었다. 예전에는 뱅크로 고정해서 뽑았기 때문에
`pool-extra` 의 **186문항이 한 번도 출제되지 않았다** (`take()` 가 뱅크 고갈 시에만
폴백했는데, 뱅크가 마르는 경우가 없었다). `stages` 를 파일이 아니라 `ch` 로 거르니
그 문항들이 자동으로 후보에 들어온다. 전체 출제 가능 문항이 178개 → 296개가 됐다.

### 자리 태그를 세게 걸면 축이 무너진다

`where` 필터를 넣자마자 **sp(속도) 축이 4문항까지 떨어졌다.** 원인은 이렇다.

- `phone` 태그 문항은 sp 를 14%만 잰다 (`room`·`meal`·`hall` 은 0%)
- 자리가 맞는 문항을 최우선으로 뽑게 했더니 아침·교실·밤 15칸이 그런 문항으로 찼다

축이 4문항이면 `score.ts` 의 `normalize` 에서 `room <= 0` 이 되어 그 축이 0으로 눌리고,
유형 코드 첫 글자(F/S)가 사실상 동전 던지기가 된다.

두 가지로 막았다.

1. **`PLACE_CAP`** — 한 장면이 장소 특정 문항을 3개까지만 가져간다. 장면 맛은 나되 도배는 안 된다
2. **보정 패스** — 다 채운 뒤 하한(축당 8문항)에 못 미친 축이 있을 때만, 그 축을 안 재는 문항
   하나를 같은 장면의 다른 후보로 바꿔 끼운다. 하한을 넘겼으면 아무것도 안 한다

`npm run check:questions` 가 이 하한을 4,800조합 전부에서 검사하고, 깨지면 실패한다.

## 채점은 왜 그렇게 생겼나

`score.ts` 의 정규화는 v1에서 검증된 것이라 **바꾸지 않는 게 좋다.**

점수를 그냥 더하면 "그 사람에게 어떤 문항이 뽑혔는지"가 결과에 섞여 들어간다.
사람마다 문항이 달라지는 구조에서는 치명적이다. 그래서 이렇게 한다.

1. 그 세트를 **무작위로 찍었을 때의 기댓값**을 구한다 → 이게 판정선
2. 실제 점수가 거기서 얼마나 벗어났는지 본다
3. 그 방향으로 갈 수 있었던 **최대 이탈폭**으로 나눈다

세트가 어느 쪽으로 치우쳐 있든 판정선이 자동으로 가운데 온다.

## 문항을 손봤으면 반드시 이걸 돌린다

```bash
npm run check:questions
```

자기소개 조합 4,800가지를 전부 돌려서 확인한다.

- 문항 자리 35개가 전부 채워지는지 (조건 문항 때문에 뱅크가 마르면 조용히 빠진다)
- 같은 문항이 두 번 안 나오는지
- 16개 유형에 다 도달할 수 있는지
- **축마다 8문항 이상이 실제로 재고 있는지** (아래 "자리 태그를 세게 걸면" 참고)

## 알고 있는 한계

- **공유 썸네일이 SVG다.** 카카오톡·페이스북은 SVG를 못 읽는다. 공개 전에 PNG로 바꿔야 한다 (`docs/ART-MANIFEST.md`)
- **결과 화면이 임시다.** 유형 코드와 축 게이지만 나온다. 결과 내용은 따로 작업 중
- **문항 364개가 전부 번들에 들어간다** (gzip 50KB). 실제로 쓰는 건 35개뿐이라 나중에 나눠 실을 수 있다. 지금은 문제 될 규모가 아니다
- **v1 `index.html` 이 아직 저장소에 있다.** GitHub Pages 데모를 살려두려고 남겼다. Cloudflare로 옮기고 나면 지우면 된다
