# 인수인계 — 문항 설계를 맡은 쪽에게

이 저장소에서 **문항·서사·결과를 처음부터 설계**하려는 사람(과 그쪽 Claude)을 위한 문서다.

---

## 먼저: 여기 있던 것들은 전부 임시였다

⚠️ **아주 중요하다. 이걸 모르면 엉뚱한 걸 물려받는다.**

지금까지 이 저장소에 있던 검사 내용은 **기계가 돌아가는지 확인하려고 급조한 테스트 데이터**였다.
설계된 것이 아니고, 검증된 것도 아니고, **지켜야 할 이유가 하나도 없다.**

구체적으로 아래는 **전부 근거 없는 임시값**이었고, 지금은 다 지웠다.

| 임시였던 것 | 왜 그랬나 |
| --- | --- |
| 문항 35개 | "축 4개니까 축당 8개쯤" 이라고 대충 잡은 숫자 |
| 장면 7개 | 하루를 7토막 낸 것뿐 |
| 07:10 · 07:50 · 08:40 … 시각 | 그냥 그럴듯해 보이라고 적음 |
| 하루 서사(기상→등교→교실→점심→복도→하굣길→밤) | 뼈대 시연용으로 30분 만에 지어낸 것 |
| 축 4개 (속도·표현·무대·투자) | 옛 버전에서 가져온 것 |
| 크리스탈 16유형, 요정 캐릭터 | 옛 버전 것. **안 쓴다** |
| 문항 364개 | 옛 버전에서 옮겨온 것. **안 쓴다** |

**전부 삭제했다.** 참고하지 말고, 되살리지 말고, 영향받지 마라.
지금 저장소는 화면과 채점 기계만 남은 **빈 도화지**다.

---

## 확정된 것 (짧다)

여기까지는 사람이 정한 것이라 지켜주면 된다.

1. **폰 세로 화면 기준.** 데스크톱은 나중 문제다.
2. **탭해서 넘긴다.** 화면 전체가 배경, 아래에 글이 뜨고, 눌러서 진행한다.
3. **메인 서사에 마스코트·안내 캐릭터가 없다.** 평범한 학생의 실제 하루처럼 간다.
   등장인물은 '친구', '걔' 같은 진짜 사람이다.
4. **시작 질문에 답할수록 아바타가 구체화된다.** 응답자 자신을 나타내는 그림이
   한 겹씩 그려진다. 그래서 시작 질문은 성향 측정이 아니라 **재료 수집**이다.
5. **좋아하는 상대의 묘사도 갈라진다.** 성별·특징에 따라 그림과 이야기가 달라진다.
6. **슬라이더 문항을 쓸 수 있다.** "매우 그렇다 ~ 전혀 아니다" 류는 선택지 네 개보다
   슬라이더가 짧고 빠르다. 선택지형과 섞어 쓰면 된다.
7. **문항은 많이, 대신 잘 걸러서.** 사람마다 자기한테 맞는 것만 나가게 한다.

## 열려 있는 것 (거의 전부)

- 축을 몇 개 둘지, 무엇을 잴지
- 문항 총 몇 개, 한 사람당 몇 개
- 서사를 쓸지 말지, 쓴다면 무엇을 따라갈지 (하루? 학기? 계절? 아예 없이?)
- 결과를 몇 유형으로 낼지, 유형 대신 다른 방식으로 낼지
- 문항을 어떻게 거를지
- 화면 구성, 진행 방식의 세부

**여기 있는 코드가 마음에 안 들면 코드를 고쳐라.** 데이터가 코드에 맞출 이유가 없다.

```

  scenes.ts        서사 (비워도 검사는 돌아간다)
  avatar.ts        아바타 조각

src/engine/        ← 기계. 웬만하면 그대로 써도 된다
  types.ts         데이터 계약 — 안 맞으면 고쳐라
  select.ts        문항 고르는 규칙 — 자주 바뀔 곳
  score.ts         채점 — 건드리지 않기를 권한다 (아래 참고)

```

각 파일 맨 위에 무엇을 어떻게 채우는지 예시와 함께 적어뒀다.

지금 사이트를 열면 **"검사할 내용이 비어 있어"** 라고 뜬다. 정상이다.
`axes.ts` · `intro.ts` · `questions.ts` 세 개가 차면 자동으로 검사가 돌아간다.

## 데이터 계약

`src/engine/types.ts` 에 전부 있다. **제안이지 확정이 아니다.**

### 축

```ts
{ id: 'speed', name: '속도', posLabel: '금사빠', negLabel: '늦사빠' }
```

개수 자유. 다만 축이 늘면 축당 문항이 필요해지고(대략 6~8개),
유형으로 결과를 낼 거면 유형 수가 2^n으로 늘어난다.

### 선택지형 문항

```ts
{
  id: 'q-001', kind: 'choice',
  text: '쉬는 시간 10분.\n걔가 혼자 앉아 있다.',
  tags: ['classroom'],
  show: { gender: 'f' },              // 조건 (생략 가능)
  options: [
    { text: '가서 말 건다',      score: { express: 3 } },
    { text: '지나가는 척 근처로', score: { express: 1 } },
    { text: '그냥 본다',         score: { express: -2 } },
  ],
}
```

### 슬라이더형 문항

```ts
{
  id: 'q-002', kind: 'scale',
  text: '읽씹당하면 하루 종일 신경 쓰여',
  minLabel: '전혀', maxLabel: '완전',
  steps: 5,
  weight: { invest: 3 },
}
```

응답 위치를 -1~+1로 환산해 `weight` 를 곱한다. 가운데면 0점.
`steps` 를 홀수로 두면 중립이 생기고, 짝수면 반드시 한쪽을 고르게 된다.

### 특성 (traits)

선택지가 붙이는 꼬리표. 세 군데에 쓰인다.

```ts
{ text: '여자', traits: { gender: 'f' } }
```

1. **아바타** — 어떤 조각을 그릴지
2. **상대 묘사** — 어떤 그림·이야기로 갈지
3. **출제 조건** — `show: { gender: 'f' }`

### 장면 (선택)

```ts
{
  id: 'classroom', title: '같은 반이 됐다', label: '3월 · 교실',
  art: { src: '...', alt: '...', variants: [{ when: { crushGender: 'm' }, src: '...' }] },
  beats: [
    { kind: 'narration', text: '교실에 들어선다.' },
    { kind: 'line', speaker: '친구', text: '야 저기 봐.' },
    { kind: 'question', pick: { tags: 'classroom' } },
  ],
}
```

**장면이 하나도 없으면 문항만 순서대로 나간다.** 서사 없이 시작해도 되고,
문항이 정해진 다음에 서사를 얹어도 된다.

## 채점만은 그대로 두기를 권한다

`src/engine/score.ts` 의 정규화 방식이다.

점수를 그냥 더하면 **"그 사람에게 어떤 문항이 뽑혔는지"가 결과에 섞여 들어간다.**
조건부 출제 때문에 사람마다 문항이 달라지는 구조에서는 치명적이다.
예를 들어 어떤 사람에게 '직진' 쪽 점수를 주는 문항이 우연히 많이 뽑히면
그 사람은 실제 성향과 무관하게 직진으로 판정된다.

그래서 이렇게 한다.

1. 그 세트를 **무작위로 찍었을 때의 기댓값**을 구한다 → 이게 판정선
2. 실제 점수가 거기서 얼마나 벗어났는지 본다
3. 그 방향으로 갈 수 있었던 **최대 이탈폭**으로 나눈다

세트가 어느 쪽으로 치우쳐 있든 판정선이 자동으로 가운데 온다.
축이 몇 개든, 문항이 선택지형이든 슬라이더형이든 그대로 돈다.

## 작업 방법

```bash
npm install
npm run dev              # http://localhost:4321
npm run check:questions  # 문항 손봤으면 반드시
npm run build
```

### `npm run check:questions` 가 잡아주는 것

눈으로는 못 잡는 것들이다. 문항을 손볼 때마다 돌려라.

- id 중복
- 어떤 축도 재지 않는 문항 (있어도 결과에 영향이 없다)
- 없는 축을 가리키는 문항 (오타)
- 축별 문항 수 불균형 (6개 미만이면 경고)
- **아무에게도 안 나가는 문항** — `show` 조건이 실제 특성 조합과 안 맞는 경우
- **사람마다 출제량 차이** — 어떤 사람은 10문항, 어떤 사람은 40문항 받는 상황
- 중복 출제
- 무작위 응답으로 채점까지 돌려서 터지는지

## 오늘 정하면 좋은 것

순서대로 정하면 뒤가 쉬워진다.

1. **무엇을 재는가** — 축. 이게 정해져야 문항을 쓸 수 있다
2. **결과를 어떤 모양으로 낼 것인가** — 유형? 점수? 서술형?
   (축 개수가 여기서 역산된다)
3. **시작 질문 목록** — 아바타 재료 + 분기 조건.
   순서 = 아바타가 그려지는 순서이므로 큰 것부터
4. **문항** — 축마다 최소 6~8개. 조건부 문항은 더 넉넉히
5. **한 사람당 몇 문항** — 옛 버전 100문항은 길다는 피드백이 있었다.
   너무 적으면 결과가 찍기와 구별이 안 된다
6. **서사** — 쓸지 말지부터. 문항이 먼저 나오고 나중에 얹어도 된다

## 참고: 지난번에 걸렸던 것들

같은 실수를 반복하지 않도록 남긴다.

- **선택지 개수가 들쭉날쭉하면** 화면 높이가 매번 바뀌어서 눈이 피로하다.
  4개면 4개로 통일하는 게 낫다.
- **선택지가 길면** 두 줄로 넘어가면서 화면 아래쪽이 넘친다. 상한을 정해두면 좋다.
- **문항이 장면 맥락과 안 맞으면** 몰입이 깨진다.
  아침에 눈 뜨는 장면에서 "연애를 안 하는 이유는?" 이 나오는 식이었다.
  `tags` 로 묶어두면 `pick` 으로 걸러낼 수 있다.
- **밝은 일러스트 위에 흰 글씨**는 안 읽힌다. 문항 박스가 자기 바닥을 깔도록
  이미 처리해뒀지만, 그림이 들어오면 다시 확인이 필요하다.
